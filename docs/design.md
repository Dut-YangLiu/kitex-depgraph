# 跨仓库静态代码分析方案(Kitex 版)

> 面向 Go 微服务(Kitex):从一个功能点追出涉及的仓库与接口调用链。
>
> 本文是方案调研的 Markdown 版，第一至八节与 [Word 版](方案调研-Kitex版.docx) 一致，第九节记录原型 v0.1 的实现情况。资料以各项目官方文档为准(查看于 2026 年 10 月)。

## 一、结论速览

- **在 Kitex、生成代码本仓和公共仓并存的情况下，现成工具在跨仓这一层基本连不上。** code-system-graph 只认 protobuf / gRPC 的生成代码，不解析 Thrift,也不识别 Kitex 生成器;codebase-memory-mcp 的跨服务连线以 HTTP 为主，文档没有提到 Kitex。
- **主路线是自建 Kitex 对齐层。** Kitex 生成代码里有稳定的锚点：生成器文件头、`NewClient(destService)`、`NewServer(handler)`、serviceInfo 里的服务名和包名，以及 stub 传给 `Call` 的线上方法名，足以把调用方和实现方精确连起来(第三节)。
- **两种生成方式可以统一:** 都用"包名.服务名/方法名"做主键;公共仓生成的还能直接按 Go 包路径匹配。同时能顺带检出同一份 IDL 在不同仓库里生成得不同步(契约漂移)。
- **现成工具可以用在仓内:** 从功能入口到 Kitex client 调用的仓内调用图，可以复用 codebase-memory-mcp(对 Go 做类型感知的调用解析)或 Go 官方工具链。
- **建议分两期落地:** 一期只扫生成代码锚点，产出服务级依赖图;二期叠加仓内调用图，做到"功能点 → 函数级调用链"(第四节)。原型 v0.1 已经把两期的主体都做了(第九节)。

## 二、问题拆解：跨仓为什么难

单个仓库内的调用图已经很成熟。难点在仓库边界:

- A 仓发起 RPC 调用时，代码里调的是生成的 client,Kitex 下就是 kitex_gen 里的 `Client` 接口，例如 `cli.GetUser(ctx, req)`;
- 真正的实现在 B 仓，两边代码没有直接引用，只能通过 IDL 契约(Thrift 或 proto 里的 service 和方法)对上;
- 所以需要一个跨仓的对齐键:gRPC 是 `/package.Service/Method`,Kitex 是 IDL 的"包名 + 服务名 + 方法名"。

"一个功能点涉及哪些仓库、接口怎么调"可以拆成两步，递归展开就是完整链路:

1. **仓内**:从功能入口(HTTP handler 或 RPC 实现)出发，沿本仓调用图找出它会走到的所有 RPC client 调用;
2. **跨仓**:按对齐键把每个 RPC 映射到实现它的仓库和方法，再从那里继续第 1 步。

## 三、Kitex 专项方案(主路线)

### 3.1 为什么现成工具连不上

- code-system-graph 的 gRPC 对齐依赖 protobuf 契约和可识别的 gRPC 生成器。Kitex 默认用 Thrift IDL,文件头也是 Kitex 自己的;
- codebase-memory-mcp 的跨服务连线以 HTTP 路由为主，能解析 .thrift 文件本身，但不会把 Kitex 调用连到实现方;
- Kitex 调用在代码里就是普通的 Go 接口方法调用，不出现 URL 或 RPC 路径字符串，靠字符串匹配的通用方案抓不到。

### 3.2 Kitex 生成代码里的锚点

| 位置 | 锚点 | 用途 |
|---|---|---|
| 每个生成文件首行 | `// Code generated by Kitex vX.Y.Z. DO NOT EDIT.` | 判定是 Kitex 生成代码，记录生成器版本 |
| 服务包内的 serviceInfo | `serviceName := "Echo"`;`Extra` 里的 `"PackageName": "api"`;`PayloadCodec` | IDL 身份：包名 + 服务名 |
| 同文件的 kClient 方法 | `func (p *kClient) Echo(...)` 内调用 `p.c.Call(ctx, "echo", ...)` | Go 方法名到线上方法名的映射(大小写可能不同) |
| client.go | `NewClient(destService string, ...)`、`MustNewClient(...)` | 调用侧入口;destService 是目标服务的注册名 |
| server.go | `NewServer(handler, ...)`、`RegisterService(svr, handler, ...)` | 服务侧入口;handler 的具体类型就是实现 |

### 3.3 对齐键

- **主键(IDL 身份)**:`PackageName.ServiceName/线上方法名`,例如 `api.Echo/echo`。调用侧和实现侧都从各自引用的生成代码里读出，和生成代码放在哪个仓库无关;
- **辅键(服务注册名)**:调用侧 `NewClient` 的 destService 对应服务端注册的服务名(如 `server.WithServerBasicInfo` 里设置的名字)。同一个 IDL 服务有多个部署实现时，用它区分实际调用的是哪一个，也方便和运行时拓扑对账;
- **destService 取值**:常量直接取;来自配置的需要解析配置文件;运行时拼接的标记为"动态",不猜;
- **若有少量 gRPC 服务**:主键换成 `/package.Service/Method`,其余流程相同。

### 3.4 两种生成形式怎么统一

| 形式 | 特点 | 匹配方式 |
|---|---|---|
| 公共仓生成 | 调用方和实现方 import 同一个 Go 包 | 直接按包路径 + 方法匹配，最稳 |
| 本仓生成 | 各仓 import path 不同，如 `order-svc/kitex_gen/…` 与 `gateway/kitex_gen/…` | 读 serviceInfo 的 PackageName + ServiceName,算出主键再匹配 |
| 混合 | 同一个服务两种形式都有 | 全部算成主键，不用区分 |

**附带收益：契约漂移检测。** 同一主键在不同仓库的生成代码里方法集合不一致，或生成器版本差得多，说明 IDL 没有同步，可以直接作为质量门禁的检查项。

### 3.5 识别规则

- **调用侧**:凡是接收者静态类型为 Kitex 生成的 `Client` 接口的方法调用，就是一次 RPC 调用。用 go/types 判断类型，不依赖变量名，也不用管 client 存在哪个字段;
- **destService 关联**:扫描 `NewClient` / `MustNewClient` 得到注册名，沿变量、结构体字段、工厂函数追到每个调用点;
- **服务侧**:找到 `NewServer(handler, ...)` / `RegisterService(svr, handler, ...)`,确定 handler 的具体类型，它的同名方法就是这个 RPC 在本仓的入口;
- **泛化调用**:generic client 以字符串传方法名，字面量可以提取，变量则标记为动态;
- **功能入口**:功能点通常从 HTTP 接口进来(Hertz 或网关),路由注册函数也纳入调用图，作为调用链的起点。

### 3.6 已知局限

- 反射、泛化调用里用变量传的方法名、运行时拼接的 destService,静态无法确定，只能标记为动态;
- 静态调用图偏"宽"(接口分派、条件分支会带来多余的边);
- 建议用运行时链路数据(Kitex 接入的 OpenTelemetry 链路，或 SkyWalking 等的服务依赖拓扑)抽样校验：静态求全，运行时求真。

## 四、落地建议：分两期

1. **选样本**:挑一个真实功能点，横跨 3–4 个仓库，同时包含"本仓生成"和"公共仓生成"两种形式;人工画出标准调用链作为基准。
2. **一期原型**:实现锚点解析、调用侧和服务侧识别、全局关联，产出服务级依赖图，对照基准看漏报和误报。
3. **验证对齐键**:重点看 PackageName + ServiceName 在你们的仓库里是否唯一、destService 是否大多是常量或配置;这两点决定主键和辅键能不能直接用。
4. **二期**:叠加仓内调用图，实现"功能点 → 函数级链路",再封装成 MCP 工具接入评审 skill。

## 五、与代码评审 skill 的结合

- 对齐层以命令行或 MCP 工具的形式接入 Claude Code:评审时先查变更涉及的 RPC 有哪些调用方仓库，再决定要看哪些仓、找哪些 owner、跑哪些测试;
- IDL 变更单独处理：列出引用被改服务的所有调用方仓库，再比对各仓生成代码是否已同步，没同步的直接作为评审意见提出。

## 六、现成工具调研:code-system-graph

> 第六、七节是通用调研(以 gRPC 场景为主),保留作为选型依据;Kitex 的结论见第三节。

- **仓库**:github.com/dertin/code-system-graph,Rust 实现,Apache-2.0;CLI 命令 `csgraph`,数据存本地 SQLite,MCP 默认只读。
- **跨仓对齐机制**:只在证据精确匹配时建立关系。HTTP 客户端调用 + OpenAPI + 服务端路由;事件发布方 + AsyncAPI + 订阅方;GraphQL;gRPC 生成代码标记 + protobuf service + 服务端标记;字面量 SQL + 数据表;包、部署、CODEOWNERS 等。动态路由、拼接的表名、重复的提供方一律标记为"不完整/有歧义",不去猜。
- **gRPC 对齐**:解析 proto2/proto3/editions;在生成代码里识别"生成器文件头 + 规范 RPC 路径",两者缺一不可;不执行 protoc;同一 RPC 有多个提供方时标为歧义。
- **Go 支持**:HTTP 客户端只认 `net/http`,服务端认 `net/http`、Gin、Chi;字面量 SQL;Go modules。文档没有提到 Kitex / Thrift、Hertz、go-zero 的 .api、Kratos 的 HTTP 层。
- **主要风险**:粒度只到生成代码，不到业务函数;生成代码放公共仓时"业务仓 → 具体 RPC"的边可能缺失;Kitex 不在支持列表;GitHub 0 star、单人维护(2026-10-14 查看),适合借鉴设计。

## 九、原型实现(v0.1)

### 9.1 做了什么

| 方案中的项 | 原型实现 | 位置 |
|---|---|---|
| 锚点解析(3.2) | 纯语法识别，不依赖类型信息;兼容 Kitex v0.1.4 到 v0.16.1 的两种 serviceInfo 写法 | `internal/scan/kitexgen.go` |
| 调用侧识别(3.5) | go/types 判断接收者是不是生成的 `Client` 接口 | `internal/scan/analyze.go` |
| destService 关联(3.5) | 常量(含跨包)、字面量初始化的包级变量;沿局部变量、包级变量、结构体字段、工厂函数返回值追踪;追不到时退回"组件内唯一的客户端" | `internal/scan/analyze.go`、`scan.go` |
| 服务侧识别(3.5) | handler 是具体类型时直接取;是接口变量时用 CHA 在仓库内找实现，参数类型可知时比对签名 | `internal/scan/scan.go` |
| 主键 / 辅键对齐(3.3) | 先按 IDL 身份筛实现方，再按 destService 与注册名过滤;注册名来自 `WithServerBasicInfo` 或配置 | `internal/link/link.go` |
| 两种生成形式(3.4) | 不区分，统一按主键;引用同一生成包时标记为"共享生成代码" | `internal/link/link.go` |
| 契约漂移(3.4) | 同一主键各副本的方法集合比对;调用了实现方没有的方法单独报高优问题 | `internal/link/link.go` |
| 仓内调用图(二期) | 静态调用 + 接口调用(CHA)+ 函数引用(覆盖路由注册的 handler) | `internal/scan/analyze.go` |
| 功能点追踪(二期) | `trace`:从函数或 RPC 实现出发，经 RPC 跳到实现方仓库继续展开，默认只保留通向 RPC 的路径 | `internal/query/trace.go` |
| 评审集成(第五节) | `impact`:从 git diff 反向追到受影响的 RPC、上游调用方、入口函数;IDL 改动单独列出;JSON 输出 | `internal/query/impact.go` |

### 9.2 和方案相比的调整

- **不依赖构建环境。** 方案设想用 `go/packages` 逐仓加载，前提是每个仓库能 `go list`(依赖都能下载)。原型改为自己实现 importer:工作区代码和 `kitex_gen` 读源码，其余依赖一律换成空的占位包。代价是很多表达式类型无效，但分析需要的类型都在读了源码的包里，实测在 CloudWeGo 项目上没有因此漏报。好处是拿到代码就能扫，几百个包一秒内完成。
- **单进程、按目录缓存。** 方案设想"逐仓输出事实文件再全局关联"。原型在一个进程里按目录缓存类型检查结果，公共 IDL 包只加载一次;产出的 `graph.json` 就是全局关联后的事实文件，查询命令只读它。
- **加入"组件"和"库"的概念。** 真实仓库里常见一个仓库多个 main 包(easy_note),也常见共享 SDK 包装 client(gomall 的 rpc_gen)。原型按 main 包划分组件;库里的 RPC 调用沿调用图归到真正用到它的服务上。这一点方案里没有考虑到，是在 gomall 上验证时发现的。
- **CHA 加签名比对。** bookinfo 上发现，只按方法名做 CHA 会把同名的 HTTP handler 当成 RPC 实现。改为在类型可知时比对参数和返回值。

### 9.3 验证结果

见 [validation.md](validation.md)。要点:gomall 的 22 处业务 RPC 调用与人工 grep 完全一致并全部对上实现方;演示工作区里设计的 15 类场景全部由端到端测试覆盖。

### 9.4 下一步

1. **在公司仓库上试跑**:选一个横跨 3–4 个仓库的功能点，人工画出标准链路，对比 `trace` 的结果;重点看注册名(PSM 一类)能否静态求出，不能的话在配置里补 `serviceNames`。
